# ACH Maker-Checker Validation Workbench

**Config-Driven ACH Maker-Checker Validation · COO Technology Global Hackathon · control C-247489 ACH DB Next Day Validation**

> **SYNTHETIC DATA · SIMULATED SYSTEMS · PROTOTYPE.** All customers, people and values are fictional. ServiceNow,
> DMS, TNAL, GPS, ACH/AES and CheckMate are simulated by JSON files. This is not production-ready and is not a
> replacement for existing controls.

A configuration-driven first-pass validation that compares a synthetic ACH customer maintenance request (expected values)
with a synthetic TNAL/GPS-style implemented-change record (actual values), applies rules from an external YAML file, and
gives the independent checker an explainable **PASS** or **EXCEPTION**. **It automates the comparison, not the approval.**
The checker records Approve or Investigate; the maker of a change cannot.

## Quick start (one command)

| Environment | Command | Then open |
|---|---|---|
| Windows PowerShell | `.\run.ps1` | http://localhost:8000 |
| macOS / Linux / Git Bash | `./run.sh` | http://localhost:8000 |

Requirements: Python 3.11+. Node 18+ is needed **only** to rebuild the UI (`-BuildUi` / `--build-ui`); a prebuilt UI is
committed in `frontend/dist`. The scripts create `.venv`, install pinned dependencies and serve API + UI on one port.

**Run all tests and regenerate the scenario report:** `.\run_tests.ps1` or `./run_tests.sh`
→ 73 pytest tests, `reports/scenario_results.md`, `reports/scenario_results.json`, `reports/pytest_junit.xml`.

UI development with hot reload: run the API (`./run.sh`), then `cd frontend && npm install && npm run dev` (port 5173, proxies `/api`).

## Agent pipeline and AI-assisted extraction (stretch goal viii)

Every run goes through six single-responsibility agents in a fixed order. **Five are deterministic code; one uses an LLM.**

| # | Agent | Kind | Does | Never does |
|---|---|---|---|---|
| 1 | Intake | Deterministic | Schema-validates request and change record | — |
| 2 | Matcher | Deterministic | Pairs change to request (request_id + customer_id), canonical model | — |
| 3 | Document Extraction | **AI-assisted** | Reads the synthetic authorization form, returns fields + confidence, cross-checks against the request | Feed the rule engine, set PASS/EXCEPTION, approve |
| 4 | Rule Engine | Deterministic | Applies the external YAML rules → PASS / EXCEPTION | Read AI output |
| 5 | Explainer | Deterministic | Reasons from configured templates | — |
| 6 | Evidence | Deterministic | Traceable, exportable evidence pack | — |

Guardrails for the AI step, per the organizer's "AI-assisted extraction for one synthetic document type … deterministic rules,
not AI, decide control results":
- One document type only (customer authorization form, `data/scenarios/*/authorization_form.txt`, synthetic).
- Output labelled **AI-ASSISTED** with a per-field confidence; values under 0.80 are flagged "review".
- The checker must tick "I reviewed the AI-assisted values" before any decision when an extraction exists (API: `AI_REVIEW_NOT_CONFIRMED`).
- The rule engine never reads extraction output (tested: all five outcomes identical with or without it; provider failure → extraction `FAILED`, result unchanged).
- The prompt forbids approval language and treats document text as data, not instructions.

**On/off switch (`.env`).** Copy `.env.example` to `.env` and set `ACH_LLM_MODE=deterministic` (default: no LLM call, rule-based
parser, estimated tokens, labelled DETERMINISTIC) or `ACH_LLM_MODE=llm` (calls the gateway; needs `ACH_LLM_BASE_URL`,
`ACH_LLM_MODEL`, `LLM_API_KEY`). The file is re-read on every run, so the switch applies without a restart; real environment
variables override it. In deterministic mode all six agents are deterministic. If `llm` is set but the gateway is
misconfigured or unreachable, extraction shows FAILED and the validation result is unaffected.

**LLM provider.** `config/llm.yaml` → `provider: mock` (default, offline, labelled SIMULATED LLM) or `openai_compatible` for an
OpenAI-style `/chat/completions` gateway. Set the token in the environment variable named by `api_key_env`
(never in the file); optional `ACH_LLM_BASE_URL`, `ACH_LLM_MODEL`, `ACH_LLM_CA_BUNDLE` overrides.

**Token analysis tab.** Per call: input, cached input, cache-write, output tokens, latency, illustrative cost; totals, prompt-cache
hit rate, tokens avoided, cost with vs without caching. Pricing is illustrative (`pricing_per_million` in `config/llm.yaml`).

**Caching, two layers.**
1. *Provider prompt caching*: the ~1.2k-token system prompt is byte-stable and sent first, so the gateway can serve it from cache on
   every subsequent document; cached tokens are read from the gateway's `usage` (`prompt_tokens_details.cached_tokens` or
   `cache_read_input_tokens`). The mock simulates this.
2. *Local response cache*: key = sha256(prompt version, provider, model, system-prompt hash, document). A repeat costs **0 tokens**;
   the ledger records the tokens avoided. "Clear caches" on the Token analysis tab resets both for a cold-start demo.

## How to change a rule (AC4)

1. Open `config/rules/ach_db_next_day.yaml`.
2. Find rule `EVD-002` (callback verification for settlement account changes) and change `enabled: false` to `enabled: true`.
   Bump `ruleset.version` to `1.1.0` and the rule's `version` to `2` (good practice; the sha256 changes regardless).
3. Save. Within a few seconds the rule panel shows **Rule file changed since this run**.
4. Click **Re-run with new rules**. Scenario 1 changes from PASS to EXCEPTION, citing `EVD-002`. No code was changed and
   the app was not restarted.
5. Scroll to **Rule version comparison**. The baseline defaults to the config snapshot used by the earlier run and the
   candidate to the active file. Click **Compare** to see the same inputs under both versions: the rule-level diff
   (`EVD-002 enabled false → true`) and the finding that flipped.
6. Revert the edit. `config/rules/samples/ach_db_next_day.v1.1.0.yaml` holds the edited version; it can be selected in the
   comparison at any time.

What the config controls: the field dictionary (labels and normalisation: `trim`, `casefold`, `upper`, `digits_only`,
`decimal`, `sorted_csv`), which rules run and in what order, their ids, versions, severity, enable/disable, the
fields they apply to, exempt fields, approved request statuses, which evidence indicators are required and when, and the
reason text shown to the checker. Invalid edits are rejected with the exact field or YAML line, and nothing is evaluated
with an invalid rule set.

### Rule types

| Type | Organizer category | Exception | Example |
|---|---|---|---|
| `request_approved` | Request exists and is approved | `REQUEST_NOT_APPROVED` | REQ-001 |
| `required` | Required field | `MISSING_FIELD` | FLD-001 |
| `equality` | Requested vs implemented | `MISMATCH` | FLD-002 |
| `authorized_scope` | Authorization scope | `UNAUTHORIZED_CHANGE` | AUT-001 |
| `source_consistency` | GPS matches the ACH implementation | `SOURCE_INCONSISTENT` | GPS-001 |
| `evidence_present` | Evidence presence | `MISSING_EVIDENCE` | EVD-001, EVD-002 |

## Architecture

See [`docs/architecture.md`](docs/architecture.md) for the component diagram (organizer reference pattern), the process
flow showing where the prototype sits in C-247489, and the request lifecycle.

```
INPUTS (synthetic)   request.json · change.json (TNAL + GPS) · evidence indicators      ← SIMULATED systems
INGEST & NORMALIZE   schema validation → record matcher → canonical MaintenanceCase
CONTROL SERVICES     rule service (YAML, re-read per run) | validation engine | explainability
RESULTS & EVIDENCE   immutable ValidationResult: PASS/EXCEPTION, findings, rule id+version, config sha256
════════════ HUMAN-APPROVAL BOUNDARY ════════════
CHECKER EXPERIENCE   exception-first review → Approve / Investigate + comment → DecisionRecord (separate)
CROSS-CUTTING        RBAC + SoD (API-enforced) · append-only audit log · JSON logs · pytest harness
```

```

                    llm/ (prompt.py, providers.py, service.py)
                    sod.py  audit.py  store.py  evidence.py  models.py  normalize.py
backend/tests/      73 tests: every rule type, five scenarios, AC4 flip, config security, SoD, traceability,
                    agent pipeline, AI extraction (advisory), token ledger, both caches, gateway usage parsing
config/rules/       ach_db_next_day.yaml (the external rule file) · samples/…v1.1.0.yaml
config/personas.yaml  synthetic maker and checker personas
config/llm.yaml     LLM provider for the extraction agent (mock by default; gateway via openai_compatible)
data/scenarios/     s1…s5: scenario.json, request.json, change.json, expected.json
frontend/           React + TypeScript (Vite); prebuilt in frontend/dist
scripts/run_scenarios.py   writes the five-scenario results report

```

## Segregation of duties and traceability

- **Personas** (`config/personas.yaml`, synthetic): Priya Nair (P-1001, maker), Marcus Lee (P-1002, maker),
  Dana Whitfield (C-2001, independent checker). Switch in the header.
- **Enforced in the API**, mirrored in the UI: the implementer of a change gets `403 SELF_APPROVAL_BLOCKED`; any maker gets
  `403 ROLE_NOT_PERMITTED`; blocked attempts are written to the audit log.
- **Decisions** require a comment, are write-once (`409` on a second attempt) and are stored separately from the engine
  result. Approving an item with exceptions requires an explicit acknowledgement and a justification of at least 20
  characters, so the checker stays the final decision-maker without silent overrides.
- **Engine**: no approval field exists on `ValidationResult`; findings are frozen Pydantic models.
- **Per run**: run ID, request/change IDs, input sha256 digest, config file + version + sha256 (config text snapshotted to
  `runtime/configs/<sha256>.yaml`), every rule evaluation, findings digest, timestamp, then the checker decision.
  Same inputs + same config ⇒ identical findings and findings digest (tested).
- This is a prototype traceability design (FAQ Q39), not production audit retention.

## Security and data handling

- Synthetic data only. Routing numbers use the `99` prefix, which is not a valid ABA prefix, so they cannot be real.
  Email domains use `.example`.
- No credentials, secrets, internal hostnames or network calls to enterprise systems. The server binds to `127.0.0.1`
  in the run scripts.
- Config loaded with `yaml.safe_load` (no object construction), size-capped, schema-validated with unknown keys rejected,
  reason templates restricted to whitelisted placeholders (no attribute or index access).
- Inputs are schema-validated with length limits; unknown keys rejected; request and change must match on IDs.
- Persona header is a demonstration stand-in for identity; there is no authentication in the prototype.

## Assumptions (pending organizer assets and business confirmation)

1. Data is synthetic, modelled on the TNAL fields in the brief (record ID, customer ID, field, old value, new value,
   changed by, changed at). Swapping in organizer assets is a data and config change: new folders under `data/scenarios/`
   and field names in the YAML field dictionary.
2. A change record joins to a request by `request_id`; `customer_id` must also agree.
3. The request is the source of expected values; the latest TNAL row per field is the source of actual values.
4. A blank or absent requested value is reported once, as MISSING_FIELD.
5. An unauthorized change is a TNAL field whose value changed and that was not in the request.
6. Evidence is boolean indicators on the request; the required set is defined per rule in config.
7. The checker can Approve an item with exceptions only with acknowledgement and justification.
8. No volumes, handling times or savings are claimed. Production savings need the current-state baselines.

## Known limitations

- Single request + single change record per run (the minimum scope); no batch processing of a full daily CheckMate task.
- In-memory run store mirrored to `runtime/`; restarting clears the in-app history (audit file and run JSON remain).
- No authentication, real routing, correction, resubmission or revalidation workflow (out of scope). The exception queue is a
  local simulation that records where an Investigate item would go.
- Rule types are fixed in code; their parameters, order, enablement and messages are fully configurable.
